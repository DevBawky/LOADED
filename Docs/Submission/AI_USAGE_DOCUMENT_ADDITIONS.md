# LOADED AI 활용 기술 문서 추가 권장 내용

이 문서는 기존 `LOADED AI 활용 기술 문서`에 추가하거나 수정하면 좋은 내용을 정리한 보완본이다. 개발자가 결정한 게임 규칙과 설계 의도, AI가 구현과 검증에 기여한 부분이 구분되도록 작성했다.

## 1. 기존 구조 설명 수정

기존 문서의 구조도와 클래스 설명에는 현재 프로젝트에 존재하지 않는 이름이 일부 포함되어 있으므로 다음과 같이 수정하는 것이 좋다.

```text
전투 데이터: BulletData, BulletInstance, EnemyData, BattleData, StageData
상태 효과: StatusEffectController
진행 및 저장: StateManager, RunSaveData, GameStatistics
```

- `StatusEffectManager`는 실제 클래스명인 `StatusEffectController`로 수정한다.
- `BattleSaveData`는 현재 저장 구조인 `RunSaveData`로 수정한다.
- 별도 `StageManager` 대신 전투와 상점, 스테이지 전환을 관리하는 `StateManager`를 기재한다.
- 전투 구성 데이터인 `BattleData`를 데이터 계층에 추가한다.

## 2. BattleData와 StageData를 이용한 전투 및 스테이지 설계

LOADED는 전투의 구성과 스테이지 진행 순서를 코드에 직접 고정하지 않고 `BattleData`와 `StageData`로 분리했다. `BattleData`에는 전투 이름, 일반전과 보스전 구분, 보드 칸 수, 타일 프리팹, 적 생성 간격, 웨이브별 적 구성이 저장된다. `StageData`는 여러 `BattleData`를 순서대로 묶어 하나의 스테이지 진행 구조를 만든다.

개발자는 한 스테이지에 포함될 전투 수와 순서, 각 전투의 보드 크기, 웨이브 구성, 적 생성 간격, 보스 배치, 전투 종료 후 상점 진입 시점, 새 스테이지에서 초기화할 항목을 직접 결정했다. AI는 이 판단을 바탕으로 데이터를 코드와 분리하고, `StateManager`가 현재 스테이지와 전투 인덱스를 관리하며 전투, 전투 종료, 상점, 다음 전투, 다음 스테이지로 이어지도록 구현을 보조했다.

또한 현재 스테이지와 전투 위치가 저장 데이터에 포함되도록 연결하여 이어하기 시 동일한 진행 지점으로 복귀할 수 있게 했다. 음악 역시 스테이지 ID, 전투 인덱스, 보스전 여부를 기준으로 선택되도록 연결했다.

AI는 다음과 같은 구성 오류를 미리 확인하는 검증 로직 작성에도 활용했다.

- 마지막 전투가 아닌 위치에 보스전이 배치되었는지 확인
- 보드에 배치할 수 있는 수보다 적 수가 많은지 확인
- 보드 칸 수와 적 생성 간격이 허용 범위를 벗어났는지 확인
- 스테이지 또는 전투 배열이 비어 있는지 확인

이 과정에서 AI가 전투의 재미나 난이도를 결정한 것은 아니다. 전투 순서와 적 조합, 보스 배치, 보상 흐름과 수치 밸런스는 개발자가 플레이 경험을 기준으로 판단했고, AI는 그 결정을 반복 사용 가능한 데이터 구조와 전환 로직으로 옮기는 역할을 담당했다.

## 3. 아이템, 상점, 인벤토리와 공용 툴팁 시스템

아이템 시스템은 `ItemData`, `PlayerInventory`, `InventoryUI`, `ShopManager`를 중심으로 구성했다. 개발자는 아이템을 전투 중 즉시 사용하는 방식으로 정하고, 사용 자체는 턴을 소모하지 않으며 효과가 실제로 적용된 경우에만 아이템을 소비하도록 규칙을 결정했다. 인벤토리 슬롯은 3개로 제한하고, 동일한 아이템의 중복 보유는 허용했다. 아이템 희귀도는 별도로 두지 않아 상점 등장 확률을 동일하게 유지했으며, 구매한 상품은 버튼을 숨기지 않고 비활성 상태로 남도록 정했다.

AI는 이 규칙을 바탕으로 상점 구매와 골드 부족 처리, 구매 실패 시 상태 복구, 인벤토리 등록, 아이템 효과 성공 여부와 소비 처리의 연결, UI 갱신 로직을 구현하고 점검하는 데 사용했다. 또한 버튼과 상태 아이콘에서 함께 사용할 수 있는 공용 툴팁을 만들고, 마우스를 따라가면서도 화면 밖으로 벗어나지 않도록 위치 보정 로직을 작성했다.

초기 구현에서는 툴팁 관리 객체의 활성 상태에 따라 다음 탄환 정보가 갱신되지 않을 가능성이 있었다. 개발자는 실제 사용 흐름을 검토하여 툴팁 관리 객체를 항상 활성화된 Canvas 루트로 옮기는 방향을 선택했고, AI는 해당 구조에 맞게 참조와 갱신 흐름을 수정했다. 이는 AI의 첫 결과를 그대로 채택하지 않고 개발자가 위험 요소를 판단해 구조를 보완한 사례다.

## 4. 기절과 적 공격 준비 상태를 분리한 수정 사례

적이 기절했을 때 공격 타일이 사라지고 이후 공격 목록이 다시 생성되는 문제가 있었다. 처음에는 기절을 공격 취소로 처리하는 방향을 검토했지만, 개발자는 기절이 적의 예약 공격 전체를 삭제하는 것이 아니라 현재의 공격 준비만 취소해야 한다고 규칙을 명확히 했다.

이에 따라 기절 시 이미 생성된 공격 순서와 공격 아이콘은 유지하고, 현재 준비 상태와 공격 예고 효과만 해제하도록 수정했다. 기절이 끝난 적은 기존 공격을 즉시 실행하지 않고 한 턴을 사용해 다시 준비한 뒤 다음 행동에서 공격한다. 특수 적의 경우에도 실행 단계가 준비 단계로 되돌아가도록 예외 흐름을 연결했다.

추가 조사 결과 공격 아이콘이 실제로 삭제된 것처럼 보인 현상에는 렌더링 순서도 영향을 주고 있었다. 적 공격 준비 불꽃 셰이더가 기본 UI보다 늦게 그려져 기절 표시가 공격 아이콘을 덮고 있었다. AI는 상태 변경 코드, 공격 대기열 데이터, UI 계층, 셰이더 렌더 큐를 함께 추적해 원인을 좁혔고, 실제 공격 준비에 사용하는 셰이더의 렌더 순서를 수정했다.

이 사례에서 개발자는 기절의 정확한 게임 규칙과 기대 동작을 결정했다. AI는 그 기준에 따라 공격 대기열의 유지 여부, 준비 상태 전환, 특수 적 상태 복귀, 시각적 겹침 문제를 코드 단위로 추적하고 수정안을 구현하는 데 활용되었다.

## 5. 검증 항목에 추가할 내용

| 검증 대상 | 확인 내용 | 개발자 판단과 AI 활용 |
|---|---|---|
| BattleData와 StageData | 전투 순서, 보드 크기, 웨이브, 보스 위치, 상점 전환, 저장 복원 확인 | 개발자가 진행 구조와 밸런스를 결정하고 AI가 데이터 연결과 유효성 검사를 구현 |
| 아이템과 인벤토리 | 슬롯 제한, 중복 보유, 효과 성공 시 소비, 골드 부족, 구매 실패 복구, UI 갱신 확인 | 개발자가 사용 규칙과 화면 흐름을 결정하고 AI가 시스템 간 연결과 예외 처리를 구현 |
| 기절과 공격 준비 | 공격 대기열과 아이콘 유지, 준비 상태만 취소, 기절 종료 후 재준비, 특수 적 상태 복귀 확인 | 개발자가 기절 규칙을 정정하고 AI가 상태 흐름과 렌더링 문제를 추적해 수정 |

## 7. 기존 문서에 넣기 좋은 위치

- `BattleData와 StageData` 항목은 기존 데이터 구조 설명 뒤에 배치한다.
- `아이템, 상점, 인벤토리와 공용 툴팁 시스템`은 주요 AI 활용 내역의 독립 항목으로 추가한다.
- `기절과 적 공격 준비 상태를 분리한 수정 사례`는 적 AI 또는 문제 해결 사례 뒤에 추가한다.
- 세 항목의 검증 기준은 기존 검증 표에 행으로 추가한다.
