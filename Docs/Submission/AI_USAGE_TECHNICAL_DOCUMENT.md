# LOADED AI 활용 기술 문서

## 1. 프로젝트 개요

**LOADED**는 상점에서 탄환을 직접 선택, 구매하고 강화하여 덱을 구성한 뒤, 전투에서 무작위로 장전되는 탄환의 조합과 발사 순서를 설계해 적의 예고 공격을 돌파하는 턴제 불릿 빌딩 로그라이크 게임이다.

개발 과정에서는 OpenAI Codex와 ChatGPT를 기획 구체화, 기존 Unity 프로젝트 분석, C# 구현, 디버깅, 테스트 항목 작성 및 문서화에 활용했다. GPT Image, Kling AI, Suno와 ElevenLabs는 각각 이미지, 영상, 음악과 효과음 제작에 활용했다.

AI가 게임 전체를 자율적으로 설계하도록 맡기지는 않았다. 개발자가 먼저 전투 규칙, 플레이 감각, 정보의 우선순위와 시각적 기준을 결정하고, AI에는 이를 구현하기 위한 구체적인 조건을 전달했다. AI의 결과는 코드 검토, 컴파일, Unity Play Mode 확인, WebGL 빌드 및 실제 플레이 테스트를 거쳐 채택하거나 수정했다.

본 문서는 단일 대화의 요약이 아니라 프로젝트에 남아 있는 전체 대화 기반 개발 기록, `Docs/Dev`의 날짜별 구현 문서, 현재 Unity C# 코드, ScriptableObject 에셋과 WebGL 템플릿을 서로 대조하여 작성했다. 특히 “AI가 무엇을 만들었는가”만 나열하지 않고, 개발자가 어떤 문제를 발견하고 어떤 규칙을 선택했으며 AI 결과를 왜 수정했는지를 중심으로 정리했다.

## 2. AI와 개발자의 역할

| 구분 | 개발자가 담당한 내용 | AI를 활용한 내용 |
| --- | --- | --- |
| 게임 설계 | 불릿 빌딩이라는 핵심 컨셉, 턴 규칙, 탄환 효과와 시너지 설계 | 규칙의 예외 상황 정리, 구현 가능한 데이터 구조 제안 |
| 프로그래밍 | 기능 범위, 우선순위, 입력 방식, Inspector 연결 정책 결정 | 기존 코드 분석, Unity C# 구현, 리팩터링, 방어 코드 작성 |
| UX 및 연출 | 플레이 화면을 보고 문제를 판별하고 색상, 속도, 강조 순서 결정 | UI 생성 및 수정, 애니메이션과 셰이더 연결, WebGL 대응 |
| 밸런스 | 탄환 수치와 조합 의도 결정, 실제 플레이 결과 평가 | 피해 계산 검증, 극단 조합 탐색, 예상 피해 로직 구현 |
| 콘텐츠 | 채택할 이미지, 영상, 음악 및 효과음의 기준과 최종 선택 | 여러 시안 생성과 변형 |
| 검증 | Play Mode 및 WebGL 플레이, 시각 및 청각 품질 판단 | 정적 코드 검토, 컴파일, 테스트 조건과 회귀 항목 작성 |

핵심 원칙은 **설계와 최종 판단은 개발자가 하고, AI는 분석, 구현 및 반복 수정의 속도를 높이는 도구로 사용한다**는 것이다.

## 3. 사용한 AI 도구

| AI 도구 | 활용 영역 | 주요 활용 내용 |
| --- | --- | --- |
| OpenAI Codex | 프로그래밍 | Unity C# 구현, 프로젝트 구조 분석, 리팩터링, 버그 수정, 컴파일 및 회귀 검증 |
| ChatGPT | 기획 및 개발 보조 | 기능 요구사항 구체화, 예외 상황 정리, 프롬프트 및 문서 초안 작성 |
| GPT Image | 그래픽 | 캐릭터, UI 아이콘과 오브젝트 그래픽 시안 제작 |
| Kling AI | 영상 | 정적 이미지를 기반으로 한 배경 및 캐릭터 영상 제작 |
| Suno | 음악 | 메인 메뉴, 전투, 보스, 상점과 게임 오버 BGM 제작 |
| ElevenLabs | 효과음 | 총격, 폭발, 적 공격 경고, 상태 효과와 UI 효과음 제작 |

생성된 모든 결과를 사용하는 방식이 아니라 게임의 서부극 분위기와 기능 전달에 맞는 결과만 선별했다. 사용하지 않기로 판단한 결과물은 최종 빌드에 포함하지 않았다.

## 4. AI 활용 개발 절차

```text
플레이 경험에서 문제 발견
        ↓
개발자가 의도와 우선순위 결정
        ↓
현재 프로젝트 구조와 제약 조건을 포함한 프롬프트 작성
        ↓
AI가 코드 또는 콘텐츠 생성 및 수정
        ↓
코드 검토와 컴파일
        ↓
Unity Play Mode 및 WebGL 실제 플레이 확인
        ↓
결과 채택 / 추가 수정 지시 / 폐기
```

프로그래밍 프롬프트에는 기능 이름만 적지 않고 다음 항목을 가능한 한 함께 전달했다.

- 기존 클래스와 데이터의 책임 범위
- 턴 소비 시점과 이벤트 호출 순서
- 정상 상황과 실패 상황의 기대 결과
- Inspector 참조를 유지할지 여부
- 런타임 자동 탐색 허용 여부
- 저장 및 불러오기와 WebGL 호환성
- 화면에서 확인할 수 있는 테스트 조건
- 수정하면 안 되는 기존 UI, 프리팹 및 텍스트

이 방법은 AI가 기능 하나만 국소적으로 고치면서 기존 전투 흐름이나 직렬화 참조를 깨뜨리는 문제를 줄이는 데 도움이 되었다.

## 5. 프로젝트 구조와 AI 활용 지점

### 5.1 전체 구조

LOADED의 주요 구조는 데이터, 런타임 상태, 전투 실행, 표시 계층으로 나뉜다.

```text
ScriptableObject 원본 데이터
BulletData / EnemyData / EnemyActionData / EnemyAttackData / BattleData / StageData / ItemData
                ↓
개별 런타임 상태
BulletInstance / EnemyController / StatusEffectManager / BattleSaveData
                ↓
규칙 실행과 흐름 제어
DeckManager / PlayerShoot / WaveManager / TurnManager / StageManager
                ↓
화면 표시와 피드백
PlayerCylinderUI / CombatFeedback / ActionTileUI / FirstRunGuide / WebGL Template
```

개발자는 먼저 각 계층의 책임과 데이터의 이동 방향을 결정했다. Codex에는 기존 파일, 프리팹과 Inspector 참조를 조사한 뒤 이 책임을 침범하지 않는 범위에서 구현하도록 지시했다. AI가 새 구조를 제안하더라도 기존 씬과 프리팹을 불필요하게 다시 만들거나 런타임 자동 탐색에 의존하는 방식은 채택하지 않았다.

### 5.2 탄환과 덱의 책임 분리

탄환 시스템은 다음과 같이 역할을 나누었다.

| 구성 요소 | 책임 | 개발자가 정한 핵심 원칙 |
| --- | --- | --- |
| `BulletData` | 기본 공격력, 사거리, 관통 확률, 효과와 레벨별 증가량 | 원본 에셋에는 플레이 중 변하는 값을 저장하지 않는다. |
| `BulletInstance` | 개별 탄환의 강화도, 영구 스택, 임시 보너스와 발사 시점 스냅샷 | 같은 종류의 탄환이라도 각각 다른 상태를 가질 수 있다. |
| `DeckManager` | 보유 덱, 장전 덱, 실린더, 무덤 사이의 인스턴스 이동 | 탄환을 새로 복제하지 않고 동일한 인스턴스를 이동시킨다. |
| `PlayerShoot` | 표적 결정, 피해, 치명타, 관통, 상태 효과 및 연쇄 발사 순서 | 실제 피해 계산의 단일 기준점이 된다. |
| `PlayerCylinderUI` | 실린더 순서, 다음 탄환, 강화도와 스택 표시 | 런타임 상태를 복제하지 않고 읽어서 표시한다. |

이 분리는 AI가 임의로 만든 구조가 아니다. 개발자가 “탄환 종류의 고정 정보”와 “내가 획득하고 강화한 한 발의 상태”는 달라야 한다고 판단했고, AI는 기존 코드 전반에서 그 규칙이 유지되도록 자료형과 이동 경로를 구현했다.

### 5.3 적 데이터와 행동 상태의 책임 분리

적도 정적 데이터와 현재 전투 상태를 분리했다.

| 구성 요소 | 책임 |
| --- | --- |
| `EnemyData` | 체력, 이동 특성, 아바타, 사용 행동 등 적 종류의 고정 정보 |
| `EnemyActionData` / `EnemyAttackData` | 행동 타일의 이름, 설명, 피해, 사거리 및 표시 정보 |
| `EnemyController` | 현재 체력, 위치, 방향, 행동 단계, 고정된 공격 대상과 디버프 |
| `WaveManager` | 웨이브 구성, 공용 적 프리팹 생성, 행동 순서와 턴 시간 예산 |

초기에는 적 종류마다 완성 프리팹을 두는 구조가 일부 남아 있었다. 개발자는 적을 추가할 때마다 프리팹을 복제하는 방식을 유지보수 위험으로 판단했다. 이후 `BattleData → EnemyData → WaveManager → 공용 Enemy 프리팹 → Initialize(data)` 흐름으로 바꾸었고, AI는 기존 42개 웨이브 참조를 새 구조로 옮기고 누락된 아바타 및 Animator를 경고하도록 구현했다. 새로운 적은 데이터 에셋과 아바타만으로 추가할 수 있게 되었다.

### 5.4 BattleData와 StageData: 전투 구성과 진행 순서의 데이터화

전투 콘텐츠는 씬 안에 직접 고정하지 않고 `BattleData`와 `StageData` ScriptableObject로 분리했다. 개발자는 새로운 전투를 추가할 때 씬과 Manager 코드를 복제하는 방식보다, 전투 규칙을 데이터 에셋으로 조립하는 방식이 반복 제작과 밸런스 조정에 적합하다고 판단했다.

| 구성 요소 | 저장하는 정보 | 런타임에서의 역할 |
| --- | --- | --- |
| `BattleData` | 전투 ID, 표시 이름, 시작 및 클리어 안내, 일반전 또는 보스전 구분, 보드 칸 수, 타일 프리팹, 적 등장 간격, 웨이브 배열 | `BoardManager`가 보드를 구성하고 `WaveManager`가 웨이브와 등장 간격을 적용할 때 사용하는 한 전투의 원본 설정이다. |
| `StageData` | 스테이지 ID, 표시 이름, 순서가 정해진 `BattleData` 배열 | 여러 전투를 하나의 스테이지로 묶고 다음 전투 및 다음 스테이지로 진행할 순서를 정의한다. |
| `StateManager` | 현재 스테이지 인덱스, 현재 전투 인덱스와 `GameFlowState` | `StageData`와 `BattleData`를 읽어 전투 시작, 전투 클리어, 상점, 다음 전투, 다음 스테이지 및 런 종료를 전환한다. |

실제 데이터 흐름은 다음과 같다.

```text
StateManager의 StageData 배열
        → 현재 StageData 선택
        → 현재 BattleData 선택
        → BoardCount와 TilePrefab으로 보드 구성
        → Waves와 SpawnTerm으로 WaveManager 시작
        → Battle Clear
        → Shop
        → 다음 BattleData 또는 다음 StageData
        → 더 이상 전투가 없으면 Run Complete
```

이 구조를 만들 때 개발자가 AI에 전달한 주요 조건은 다음과 같은 형태였다.

> 하나의 Stage는 여러 `BattleData`로 구성하고, 각 전투마다 보드, 전투 타입과 웨이브를 Inspector에서 설정할 수 있게 한다. 일반 전투와 보스 전투 모두 `Battle Clear → Shop → 다음 전투 또는 다음 Stage` 순서로 진행한다. 상태 전환 중에는 이동, 장전 및 발사 입력을 잠그고, 진행 중인 공격이 끝나기 전에 다음 전투가 시작되지 않게 한다. 기존 씬과 에셋 참조를 유지하고 잘못된 데이터는 실행 전에 검증한다.

AI는 기존 `BoardManager`, `WaveManager`, 상점, 보상 및 입력 잠금 코드를 조사하고 이 조건을 `StateManager`, `BattleData`와 `StageData` 사이의 책임으로 나누었다. 또한 전투가 끝나는 순간 남은 발사 코루틴과 상태 전환이 경쟁하지 않도록 행동 종료를 기다린 뒤 상태를 변경하고, 현재 인덱스를 기준으로 다음 전투 위치를 계산하는 흐름을 구현했다.

개발자는 다음 설계와 콘텐츠 값을 직접 판단했다.

- 한 스테이지에 몇 개의 전투를 배치하고 어떤 순서로 진행할지
- 각 전투의 보드 크기, 적 조합, 웨이브 순서와 등장 간격
- 마지막 전투만 보스전으로 구성하고 보스전 종료 뒤에도 상점을 거칠지
- 스테이지가 바뀔 때 덱 상태 중 무엇을 유지하고 무엇을 새 주기에 맞게 정리할지
- 전투 시작 및 클리어 문구와 스테이지 표시 이름
- 실제 플레이에서 적 밀도와 보드 크기가 회피 및 사거리 판단에 적절한지

AI가 담당한 부분은 이 판단을 재사용 가능한 데이터 구조와 안전한 전환 코드로 옮기는 작업이었다. `StateManager`의 구성 검사는 비어 있는 전투, 누락된 타일 프리팹, 비어 있는 웨이브, 잘못된 적 데이터, 보드에 들어갈 수 없는 적 수와 보스 위치 규칙을 실행 전에 차단한다. 한 웨이브의 적 수는 플레이어가 사용할 한 칸을 제외한 `BoardCount - 1`을 넘지 않아야 하며, 각 스테이지의 마지막 전투만 `Boss` 유형이어야 한다.

저장 및 불러오기에서는 `stageIndex`와 `battleIndex`를 런타임 저장 데이터에 기록한다. 불러올 때 해당 인덱스가 현재 `StageData`와 `BattleData` 범위 안에 있는지 먼저 검사한 뒤, 같은 보드와 웨이브 구성을 사용해 전투를 복원한다. 사운드 시스템도 `StageId`, 전투 인덱스, `BattleId`와 `IsBoss`를 읽어 일반 전투 및 보스전 BGM을 선택한다. 따라서 이 두 데이터는 단순한 목록이 아니라 전투 구성, 진행, 저장, 화면 안내와 사운드를 연결하는 기준 데이터다.

초기 AI 결과를 그대로 확정한 것은 아니다. 구매 성공 뒤 상점 상품이 사라지던 동작은 개발자가 의도와 다르다고 판단해 버튼을 유지하고 상호작용만 막도록 다시 지시했다. 마지막 전투 이후 즉시 런을 끝내지 않고 상점을 이용한 뒤 `Run Complete`로 전환하는 규칙도 개발자 피드백으로 확정했다. 이를 통해 AI가 흐름을 임의로 결정한 것이 아니라, 개발자가 플레이 순서와 보상 리듬을 정하고 AI가 상태 전환과 예외 처리를 구현했다는 점을 구분할 수 있다.

### 5.5 AI 산출물에 대한 책임 범위

개발 기록 중 일부에는 “사용자가 직접 수정한 코드는 없음”이라고 적혀 있다. 이는 키보드로 C# 코드를 직접 입력하지 않았다는 뜻이지, AI가 게임을 자율적으로 설계했다는 뜻은 아니다. 다음 항목은 일관되게 개발자가 결정했다.

- 핵심 재미인 탄환 순서 조작과 덱 빌딩의 규칙
- 어떤 탄환 및 상태 효과가 존재하고 서로 어떻게 결합되는지
- 적별 행동 패턴, 공격 예고 단계와 회피 가능성
- 보스의 고정 행동 순서와 페이즈 전환 시점
- 턴 소비, 표적 유지, 사망, 기절 및 막힘 상황의 처리 원칙
- UI 배치, 색상, 강조 순서, 애니메이션 강도와 사운드 전달력
- AI 결과를 채택할지, 다시 수정할지, 제거할지에 대한 최종 판단

AI는 이 판단을 코드로 옮기고, 많은 조합을 빠르게 점검하며, 누락된 예외 상황을 제시하는 구현 보조 도구로 사용했다.

## 6. 주요 AI 활용 사례

### 6.1 스테이지 타일 중앙 정렬: 결과 조건을 수식으로 전달

**사용 AI:** OpenAI Codex  
**개발자 판단:** 타일 수가 달라져도 화면의 중심이 흔들리지 않아야 하며, 홀수와 짝수 배열 모두 중앙 대칭이어야 한다.

대표 지시 사항은 다음과 같다.

> `BoardCount`만큼 타일을 생성하고 `BoardDistance` 간격으로 X축에 배치한다. 홀수 개라면 중앙 타일을 로컬 좌표 0에 두고, 짝수 개라면 중앙의 빈 공간을 기준으로 좌우 대칭이 되게 한다. 기존 Inspector 참조를 유지하고 null 참조와 중복 생성을 방지한다.

초기 AI 결과는 시작점에서 한쪽 방향으로만 타일을 생성해 보드가 치우쳤다. 개발자는 이를 채택하지 않고 기대 좌표를 다시 명시했다. 수정 결과는 다음 공식을 사용한다.

```text
startOffset = -(BoardCount - 1) × BoardDistance × 0.5
positionX = startOffset + BoardDistance × index
```

이 사례 이후에는 “중앙 정렬”처럼 해석이 갈릴 수 있는 표현 대신 홀수 및 짝수 예시, 좌표 기준과 유지해야 할 직렬화 참조까지 프롬프트에 적었다.

### 6.2 탄환 데이터: 확률과 효과의 의미를 개발자가 먼저 정의

**사용 AI:** OpenAI Codex  
**개발자 판단:** 탄환의 능력은 데이터로 확장할 수 있어야 하지만, 각 수치가 뜻하는 바는 전투 결과와 정확히 일치해야 한다.

개발자가 지정한 탄환 데이터에는 기본 피해, 사거리, 치명타, 관통과 여러 상태 효과가 포함된다. 특히 관통은 단순한 `가능/불가능` 값이나 최대 관통 횟수가 아니다. 관통 배열의 각 값은 “현재 적을 맞힌 뒤 다음 적에게 진행할 확률”을 의미하며 첫 타격은 항상 보장된다. 따라서 최대 타격 수는 배열 길이보다 1 크다.

```text
첫 번째 적: 항상 타격
penetration[0] 성공: 두 번째 적 타격
penetration[1] 성공: 세 번째 적 타격
...
```

독, 기절, 표식, 넉백, 위치 교환, 흡혈과 약화는 한 탄환에 여러 개가 존재할 수 있고 각각 독립적으로 확률을 판정하도록 했다. 표식의 받는 피해 50% 증가처럼 게임 전체에서 동일해야 하는 값은 각 탄환에 중복 저장하지 않고 상태 시스템의 공통 규칙으로 두었다. 반대로 조준, 폭발, 도탄, 분열, 당기기처럼 당시 범위 밖의 기능은 AI가 함께 확장하지 않도록 명시적으로 제외했다.

AI의 역할은 이 의미를 직렬화 가능한 데이터 구조와 실행 코드로 옮기는 것이었다. 개발자는 수치의 의미, 포함할 효과와 제외할 기능을 결정했다.

### 6.3 덱 및 실린더 생명주기와 턴 규칙

**사용 AI:** OpenAI Codex  
**개발자 판단:** 탄환은 소비품이 아니라 장전 순서와 회수 시점을 계획하는 덱 빌딩 자원이어야 한다.

개발자가 설계한 기본 생명주기는 다음과 같다.

```text
보유 덱 → 무작위 장전 → 6칸 실린더
        → 마지막에 장전된 탄환부터 발사(LIFO)
        → 발사한 탄환은 무덤으로 이동
        → 덱이 부족하면 무덤을 섞어 다시 사용
```

입력은 `R` 장전, `Space` 또는 마우스 왼쪽 버튼 발사로 정했고, 장전한 탄환 중 하나라도 턴을 소비한다면 실린더 전체 장전은 한 턴만 사용하도록 했다. 코루틴 실행 중 중복 입력을 막고, UI에는 덱을 별도로 복제하지 않고 읽기 전용 상태와 이벤트를 통해 즉시 반영하도록 지시했다.

초기 AI 구현은 발사체 오브젝트가 날아가는 방식이었다. 개발자는 게임의 빠른 총격 감각과 맞지 않는다고 판단하여 즉시 판정되는 `LineRenderer` 방식으로 바꾸었다. 이후에도 실린더 회전은 누적 회전이 아니라 슬롯에 대응하는 절대 각도로 맞추도록 수정했다. 이처럼 구현 방식의 최종 기준은 기술적 편의보다 개발자가 의도한 플레이 감각이었다.

마지막 적을 이미 처치했는데 남은 탄환까지 허공으로 소비되는 문제에서는 개발자가 플레이어 의도를 다음과 같이 구분했다.

- 적을 향해 발사를 시작했다면 마지막 적이 죽은 시점에 멈추고 남은 탄환을 보존한다.
- 처음부터 사거리 안에 적이 없었다면 의도적인 허공 발사로 보고 실린더 전체를 소비한다.
- 발사 도중 상황이 변해도 처음 정한 모드를 바꾸지 않는다.

AI는 매 발 현재 체력, 보호막과 이미 예약된 피해를 포함해 생존 표적을 다시 검사하도록 구현했다. 개발자는 관통, 연쇄 발사, 상태 피해 및 마지막 적 처치 등 실제 플레이 사례로 이 규칙이 보존되는지 확인했다.

### 6.4 개별 탄환 강화와 덱 빌딩

**사용 AI:** OpenAI Codex  
**개발자 판단:** 같은 탄환 종류를 여러 장 보유하더라도 각 사본의 강화도와 누적 효과는 독립적이어야 한다.

처음에는 `BulletData` 하나를 여러 탄환이 공유하므로 그 에셋에 강화도를 저장하면 같은 종류의 모든 탄환이 동시에 강화되는 문제가 있었다. 개발자는 원본 데이터와 소유한 카드의 상태를 분리해야 한다고 판단했다. AI는 `BulletInstance`를 도입하여 다음 상태가 덱, 실린더와 무덤을 이동해도 유지되도록 구현했다.

- 최대 `+3`의 개별 강화도
- 레벨별 공격력, 치명타, 효과, 조건부 보너스 및 관통 수치
- 충전형 탄환처럼 전투 중 쌓이는 영구 또는 임시 스택
- 다음 탄환 표시와 관리 UI에 필요한 개별 색상, 레벨 및 스택

개발자가 이미 배치한 탄환 관리 Canvas와 `Button _ My Bullet`의 레이아웃 및 앵커는 유지하고 기능만 연결했다. 관리 화면의 배치, 강화 비용과 실제 밸런스 값은 개발자가 결정했다. 덱이 거의 비었을 때 “다음 탄환” 미리보기가 끊기는 문제에는 무덤을 조금 일찍 재순환하여 정보가 사라지지 않도록 보완했다.

이 작업에서 AI는 덱 빌딩을 새로 발명한 것이 아니라, 개발자가 설계한 “각 탄환이 하나의 성장 가능한 개체”라는 원칙을 전체 생명주기에서 잃지 않도록 구현했다.

### 6.5 탄환 조합과 밸런스 분석: 설계 결정을 위한 계산 보조

**사용 AI:** ChatGPT, OpenAI Codex  
**개발자 판단:** 강한 시너지는 허용하되, 어떤 처리 순서 때문에 강해지는지를 이해한 뒤 최종 밸런스를 결정해야 한다.

개발자는 독을 누적하고 증폭한 뒤 `베놈 버스트`로 소비하는 조합을 가장 강한 빌드로 예상하고 직접 설계했다. AI에는 탄환 이름만 보고 평가하지 말고 실제 코드의 발사 순서, 강화 수치, 독 스택, 증폭 배율, 클론의 복사 범위와 버스트 소비 시점을 추적하도록 지시했다.

분석 결과 기본 설계안인 `독 누적 → 증폭 → 베놈 버스트`가 강한 것은 맞았지만, 당시 구현에서는 클론 탄환이 직전 탄환의 런타임 스냅샷과 증폭된 효과까지 복사할 수 있어 예상보다 훨씬 큰 반복 증폭이 가능했다. 최대 강화와 이상적인 순서를 가정한 분석에서는 기본 독 조합이 수만 단위인 반면 클론을 섞은 변형은 수백만 단위의 피해까지 증가했다. 실제 개발 기록의 오버킬 회귀 테스트에도 베놈 버스트 피해 `3,159,568`의 계산 사례가 남아 있다.

이 수치는 실전에서 항상 재현되는 평균 피해가 아니라, 특정 순서와 최대 조건을 전제로 한 상한 분석이다. AI가 자동으로 하향 조정하지는 않았다. 개발자가 다음 질문을 판단할 수 있도록 원인을 제시하는 데 사용했다.

- 클론이 직전 탄환의 원본 능력만 복사할지, 누적된 런타임 상태까지 복사할지
- 증폭에 상한을 둘지, 높은 고점을 덱 완성 보상으로 유지할지
- 무작위 장전에서 해당 순서를 만들 난이도가 피해 상한에 비례하는지
- 툴팁과 피해 예상치가 실제 처리 순서를 충분히 설명하는지

즉 탄환과 시너지는 개발자가 만들었고, AI는 코드 경로를 따라 조합 순위를 비교하고 설계자가 놓치기 쉬운 상한을 수치화하는 분석 도구로 활용했다.

### 6.6 실제 전투와 피해 예상치의 일치

**사용 AI:** OpenAI Codex  
**개발자 판단:** 미리보기는 모든 가능성을 과장해서 보여 주는 기능이 아니라, 플레이어가 확실히 얻을 결과만 신뢰할 수 있게 보여 주어야 한다.

실린더에서 탄환에 마우스를 올리면 첫 발부터 해당 슬롯까지의 누적 예상 피해를 적 체력바에 표시하도록 설계했다. 개발자는 기본 피해와 확률 100%인 치명타, 관통, 효과 및 연쇄만 포함하고, 100% 미만의 무작위 결과는 제외하도록 했다. 실제 발사 코드와 다른 간이 계산식을 만들면 두 결과가 어긋날 수 있으므로 AI에는 발사 시점의 동일한 스냅샷과 처리 순서를 재사용하도록 지시했다.

충전형 탄환은 장전된 동안 발생한 실제 발사 횟수를 세며 연쇄 발사도 포함한다. 클론은 단순히 같은 이름의 탄환을 만드는 것이 아니라 직전 발사의 능력, 영구 스택, 저장 및 임시 보너스와 발사 횟수 스냅샷을 복사한다. AI는 이 런타임 문맥을 예상치 계산에도 동일하게 전달했다.

첫 UI 결과에서는 여러 이미지를 겹쳐 구간 사이에 틈이 생겼고, 약한 첫 피해가 둥근 체력바의 투명한 가장자리에 가려졌다. 개발자는 이를 실제 화면에서 발견해 한 장의 직사각형 오버레이에 구간을 그리는 방식, 현재 체력 기준 재계산, 발사 슬롯의 고유 색상 사용을 요청했다. AI는 계산과 렌더링을 수정했고 개발자는 실제 발사 전후 체력값과 시각적 길이를 비교했다.

### 6.7 적 AI의 공통 설계 원칙

**사용 AI:** OpenAI Codex  
**개발자 판단:** 로그라이크의 변동성은 탄환 조합에서 만들고, 적 행동은 관찰, 예측 및 대응할 수 있어야 한다.

적의 전투 행동 선택에는 원칙적으로 난수를 사용하지 않는다. 이동, 회전, 재장전, 행동 등록, 공격 준비와 공격 실행을 한 턴에 합치지 않고 각각 별도의 플레이어 턴에 대응시켰다.

```text
방향이 다르면 회전
→ 빈 행동 슬롯 표시
→ 행동 타일 등록
→ 목표 타일 및 방향 고정과 공격 준비
→ 다음 턴에 고정된 정보대로 실행
→ 회복 또는 재장전
```

핵심 프롬프트는 다음과 같은 의미였다.

> 공격 준비 시점에 목표 타일과 방향을 저장한다. 실행 직전에 플레이어를 다시 추적하지 않는다. 공격과 지원 모두 행동 타일로 먼저 알리고, 이동, 회전 및 재장전을 같은 턴에 함께 처리하지 않는다. 전방의 다른 적에게 막힌 적은 아군을 관통해 공격하지 않는다.

이 원칙 덕분에 플레이어는 예고된 타일에서 이동해 공격을 피할 수 있다. 투척 공격의 고정 타일로 다른 적이 들어오면 그 적이 맞고, 총잡이의 사선에 아군이 들어오면 발사를 기다리거나 실행 시 피해를 주지 않는다. 이는 AI가 승률을 최대화하도록 만든 적이 아니라, 개발자가 정한 공정한 퍼즐 규칙을 상태 머신으로 실행하는 적이다.

### 6.8 적 종류별 결정 규칙

개발자는 적마다 플레이어가 읽을 수 있는 고유한 행동 문법을 만들었고, AI에는 이를 명시적인 상태 전이로 구현하도록 했다.

| 적 종류 | 개발자가 설계한 행동 규칙 | AI 구현 시 중요했던 예외 |
| --- | --- | --- |
| 칼잡이 | 방향 전환 → 근접 행동 등록 → 접근 → 인접 시 준비 → 다음 턴 공격 → 선호 거리로 후퇴 | 첫 공격은 보장하고, 인접한 상태에서는 불필요한 무작위 선택 없이 준비한다. |
| 총잡이 | 방향 전환 → 사격 등록 → 보드 끝까지 사선 고정 → 다음 턴 발사 → 재장전 | 전방 적에게 막히면 준비 상태를 유지하고 기다리며 아군 오사를 만들지 않는다. |
| 투척병 | 투척 등록 → 플레이어가 서 있던 타일 고정 → 다음 턴 투척 → 회복 | 플레이어가 이동하면 빗나가고, 그 타일에 다른 적이 들어오면 해당 적이 맞는다. |
| 지원형 적 | 지원 등록 → 대상 고정 → 다음 턴 회복 또는 보호막 → 충전 소모 | 체력 비율이 낮은 아군을 우선 회복하고 동률이면 타일 인덱스로 결정한다. 유효하지 않은 대상에는 충전을 쓰지 않는다. |

칼잡이와 총잡이는 플레이어 기준 가장 앞에 있는 같은 전선의 적만 행동하고, 뒤에 있는 경우 회전한 뒤 대기하도록 했다. 투척병과 지원형은 후방에서도 역할을 수행한다. 지원 대상 선택은 “체력 비율이 기준 이하인 아군 중 가장 낮은 비율, 동률이면 낮은 타일 인덱스”처럼 재현 가능한 규칙을 사용한다. 회복 예고는 초록색, 보호막 예고는 청록색으로 구분했다.

AI는 상태 전이, 점유 검사와 실패 처리를 구현했다. 개발자는 각 적이 한눈에 구분되는지, 한 턴에 너무 많은 행동을 하지 않는지, 예고를 보고 실제로 대응할 수 있는지를 플레이하며 조정했다.

### 6.9 보스 Big Barrel: 개발자가 작성한 행동표를 상태 머신으로 변환

**사용 AI:** OpenAI Codex  
**개발자 판단:** 보스는 일반 적보다 복잡하지만, 정해진 절차와 예고를 학습하면 피해를 피할 수 있어야 한다.

개발자는 Big Barrel의 행동을 다음과 같은 11단계 순서로 직접 설계했다.

```text
회전
→ 폭탄 행동 빈 슬롯
→ ExplosiveThrow 등록
→ 폭탄 목표 타일 고정
→ 투척
→ 선호 거리 조정
→ 산탄총 행동 빈 슬롯
→ Shotgun 등록
→ 좌우 공격 타일 고정
→ 사격
→ 재장전 및 회복
```

각 단계는 별도 적 턴이며, 준비 후 목표를 다시 계산하지 않는다. 1페이즈에는 폭탄 2개, 2페이즈에는 3개를 사용하되 체력 조건을 넘었다고 진행 중인 큰 행동을 취소하지 않고 해당 행동이 끝난 뒤 페이즈를 바꾸도록 했다. 폭탄 위치만 의도적인 예외로 무작위이며, 도화선이 1일 때 위험 타일을 표시한다.

폭탄은 일반 적처럼 타일을 점유하지 않아 플레이어, 적 및 탄환이 통과할 수 있고 상태 효과나 넉백 대상도 아니다. 폭발 시 연쇄 폭발은 각 폭탄당 한 번만 처리하며 보스도 자기 폭발 피해를 받을 수 있다. 보스 사망 시 행동 코루틴, 큐, 위험 타일과 남은 폭탄을 먼저 정리한 뒤 승리 처리하도록 지시했다.

AI는 이 행동표를 상태 머신과 코루틴으로 구현하고 공용 Enemy 프리팹에 연결했다. 행동 순서, 페이즈의 의미, 자기 폭발과 회피 가능성은 개발자가 결정했다.

### 6.10 밀치기와 턴 상호작용

밀치기는 단순한 애니메이션이 아니라 적의 예고 공격을 흐트러뜨리는 위치 제어 수단으로 설계했다. 플레이어가 바라보는 인접 적을 보드 끝 방향으로 밀되 다른 적이 있으면 바로 앞에서 멈추고, 충돌한 두 적에게 각자의 최대 체력 비율 피해를 적용한다. 전체 이동, 충돌 피해 및 사망 판정이 끝난 뒤에만 적 턴을 시작하고 3 플레이어 턴의 재사용 대기시간을 둔다.

AI에는 기존 보드 점유와 적 이동 함수를 재사용하되 플레이어 행동의 대기시간과 적 AI의 이동 판정을 섞지 않도록 지시했다. 개발자는 이 기능이 공격 예고를 무의미하게 만들지 않으면서도 전술적 탈출구가 되는지 판단했다.

### 6.11 상황 대응형 튜토리얼과 가이드 UI

**사용 AI:** OpenAI Codex  
**개발자 판단:** 튜토리얼의 원래 과제보다 플레이어 생존과 현재 수행 가능성이 우선되어야 한다.

정해진 문장만 순서대로 출력하는 초기 가이드는 적을 바라보지 않거나 사거리 밖에 있을 때 피해 예상치를 확인할 수 없었다. 또한 장전 3회나 대기를 안내하는 중 곧 피격될 상황에서도 원래 미션을 계속 요구했다. 개발자는 다음 판단을 직접 내렸다.

> 공격할 적을 바라보는 것보다 공격을 피하는 것이 우선이다. 피격 직전이라면 미션을 `적의 공격으로부터 회피하세요!`로 바꾸고 이동 버튼을 강조한다.

튜토리얼 지급 탄환의 사거리가 모두 3이라는 설계 정보도 함께 전달하여, 3칸 안에 적이 없으면 먼저 적 앞으로 이동하도록 안내하게 했다. 모든 미션에서 현재 상황상 수행할 수 없는 조건을 검사해 임시 우선 미션을 만들도록 확장했다.

```text
1. 다음 적 공격에 맞을 타일이면 회피 미션
2. 현재 미션을 수행할 수 없으면 사거리 확보 등 선행 미션
3. 대상의 반대 방향을 보고 있으면 방향 전환 미션
4. 조건이 해결되면 원래 튜토리얼 미션으로 복귀
```

개발자는 화면을 보며 시각적 결과도 반복 조정했다.

- 배경과 비슷해 눈에 띄지 않던 강조색을 빨강 또는 파랑 계열로 바꾸고 투명도를 약 13%p 낮췄다.
- 미션이 바뀔 때 패널이 잠시 커졌다 원래 크기로 돌아오게 했다.
- 우선 미션 표시는 빨간 `MISSION`으로 통일했다.
- 미션 패널에는 `다음 단계`와 `가이드 보기`만 두고, 다시 보지 않기와 닫기는 전체 가이드 패널로 옮겼다.
- `Button _ Exit` 프리팹의 기존 텍스트는 수정하지 않았고 별도의 “저장하고 나가기” 문구도 넣지 않았다.
- 두 번째 가이드의 `경고음 듣기`는 실제 적 공격 준비 셰이더와 경고음을 재사용해 1.5초 동안 상태 변화를 보여 준 뒤 원상 복구한다.
- 디버프 안내에는 표식, 독, 기절 및 약화 아이콘을 배치하고, 가이드 안에서도 마우스를 올리면 예시 스택 1의 툴팁이 나타나게 했다.
- 사용 폰트에서 굵은 글씨가 뭉개지는 문제를 확인하여 모든 가이드 텍스트의 볼드 태그를 제거했다.

이 사례는 AI가 만든 임시 시각 효과나 일반적인 UI 관습보다, 개발자가 실제 게임 화면에서 확인한 가독성, 프리팹 일관성 및 플레이 우선순위를 기준으로 결과를 수정한 과정이다.

### 6.12 전투 피드백, 콤보와 저장 범위

프로젝트 전반의 대화 기록에는 작은 수치 조정도 개발자의 플레이 판단에서 시작되었다. 예를 들어 화면 흔들림과 피격 피드백이 과하다고 느낀 뒤 강도를 약 50%로 낮췄고, 실시간 콤보 타이머는 턴제 게임과 맞지 않는다고 판단해 8턴 기준으로 변경했다. 적을 처치한 턴에는 콤보 감소를 적용하지 않고, 한 실린더로 처치한 수와 전체 콤보를 구분했다.

결과 패널의 달성 기준도 AI가 임의 생성하지 않았다. 체력 유지율, 처치 수와 오버킬 비율의 구체적인 단계는 개발자가 정하고 AI가 누적 통계와 표시를 연결했다. 적 체력은 현재값/최댓값으로 표시하고 피해 숫자는 붉은색, 확대 및 보간 효과로 조정했으며, 디버프와 적 행동 툴팁에는 고정 설명이 아니라 현재 스택, 실제 피해 및 사거리를 표시하도록 했다.

저장 시스템은 단순히 현재 스테이지만 기록하지 않는다. 개발자는 이어하기가 실제 전투 상태를 복원해야 한다고 판단하여 다음 범위를 지정했다.

- 진행 중인 런과 스테이지, 웨이브 및 턴
- 덱, 실린더 및 무덤, 탄환 강화도와 런타임 스택
- 플레이어와 적의 위치, 방향, 체력, 보호막 및 디버프
- 적 행동 단계, 고정된 공격 대상, 보스 페이즈와 폭탄
- 상점 제안 및 구매 상태, 콤보와 전투 통계

AI는 직렬화 구조와 복원 순서를 구현했다. 개발자는 “불러왔을 때 같은 판단을 이어 갈 수 있는가”를 기준으로 저장 범위를 결정했다.

### 6.13 WebGL 저장과 로딩 화면

**사용 AI:** OpenAI Codex  
**개발자 판단:** 별도 설치 없이 실행되어야 하며, 브라우저에서도 저장 안정성과 게임의 시각적 정체성을 유지해야 한다.

WebGL에서는 종료 콜백만 신뢰하기 어려워 전투 시작, 적 턴 종료, 상점 변경과 구매 완료처럼 상태가 안정된 시점에 자동 체크포인트를 저장하도록 했다. 저장 데이터는 브라우저 환경에서 사용할 수 있는 저장소에 기록하고, 기존 파일 기반 저장이 있으면 마이그레이션하도록 구성했다.

로딩 화면은 HTML과 CSS로 6칸 실린더를 표현했다. 초기 결과에서 회전축, 방향과 탄환이 생기는 약실 인덱스가 실제 게임과 달랐다. 또한 길쭉한 탄환이 외부에서 꽂히는 연출이 게임 내 UI와 맞지 않았다. 개발자는 다음 조건을 명시했다.

> 실린더는 시계 방향으로 정확히 60도씩 회전해야 한다. 회전이 끝난 뒤 정렬된 약실에 탄환이 바로 나타나며, 별도의 긴 탄환 삽입 연출은 사용하지 않는다.

AI는 CSS의 회전 중심, 절대 각도와 약실 인덱스 계산을 수정했다. 이 변경은 Unity 코드가 아니라 WebGL 템플릿 변경이므로, 로딩 화면만 고치는 경우 Unity 콘텐츠를 다시 빌드할 필요가 있는지 빌드 산출물 반영 방식도 함께 확인했다.

### 6.14 이미지, 영상, 음악 및 효과음 제작

그래픽과 영상은 AI가 만든 첫 결과를 그대로 사용하는 대신 다음 기준으로 선별했다.

- 서부극과 픽셀 아트의 색감이 기존 UI와 일치하는가
- 작은 아이콘에서도 기능을 알아볼 수 있는가
- 반복 영상의 시작과 끝이 자연스럽게 연결되는가
- 캐릭터 실루엣과 이동 방향이 게임 플레이를 방해하지 않는가

Kling AI로 제작한 기차역 배경 영상에는 영상 길이, 기차의 이동 방향, 등장 시점, 통과 시간과 먼지가 사라지는 시간을 구체적으로 지정했다. 반복 구간이 어색하거나 게임 화면과 원근이 맞지 않는 결과는 제외하고 필요한 부분만 편집했다.

Suno에는 일반 전투, 보스전, 상점과 메인 메뉴의 역할을 나누어 서부극 및 플라멩코 계열 악기, 템포와 공격성을 지시했다. ElevenLabs 효과음은 총격, 폭발, 경고음, 상태 효과와 UI 피드백 용도로 생성했다. 기계적이거나 미래적으로 들리는 결과, 다른 효과음에 묻혀 정보 전달이 약한 결과는 채택하지 않았다. Kling AI, Suno와 ElevenLabs 결과물은 모두 에셋 생성 당시 프리미엄 구독 상태에서 제작했으며, 생성 기록과 구독 증빙을 별도로 보관할 수 있다.

## 7. 검증 방법과 개발자 판단

### 7.1 기본 검증 절차

AI 결과는 작업 성격에 따라 다음 단계로 검증했다.

1. 수정 파일과 영향 범위를 확인한다.
2. 상태 변경 순서, null 처리, 턴 소비와 저장 시점을 코드로 검토한다.
3. `dotnet build`로 C# 컴파일 오류와 경고를 확인한다.
4. Unity Play Mode에서 정상 입력과 예외 상황을 재현한다.
5. UI, 애니메이션, 사운드와 셰이더는 실제 화면과 게임 분위기를 기준으로 확인한다.
6. WebGL 전용 기능은 브라우저 빌드에서 로딩, 오디오 활성화, 저장 및 불러오기와 화면 배치를 확인한다.
7. 요구사항을 충족하지 못하면 추가 지시하거나 직접 값을 조정하고 다시 검증한다.

정적 코드 검토나 컴파일만 수행한 항목은 실제 플레이 검증이 끝난 것처럼 기록하지 않았다. 개발 기록에는 검증한 범위와 수동 확인이 남은 범위를 구분하여 작성했다.

| --- | --- | --- |

| 장전 및 대기 안내 중 피격 위험이 생김 | 튜토리얼 진도보다 생존이 우선 | 모든 미션보다 회피 우선순위를 높임 |
| WebGL 실린더가 반대로 돌고 다른 약실에 탄환이 생김 | 게임 내 실린더와 동일한 규칙이어야 함 | 시계 방향 60도 절대 회전과 정렬 후 탄환 표시 |

### 7.4 개발자가 최종 판단한 이유

AI는 컴파일 가능한 구현과 다수의 예외 조건을 빠르게 만들 수 있었지만, 다음 판단은 자동 검증만으로 결정할 수 없었다.

- 적의 예고가 충분히 공정하면서도 긴장감을 유지하는가
- 강한 탄환 시너지가 버그인지, 어려운 덱 완성에 대한 보상인지
- 피격, 반동 및 화면 흔들림이 강렬함과 불편함 사이에서 적절한가
- 튜토리얼 강조가 게임의 분위기보다 정보 전달을 우선해야 하는 순간은 언제인가
- 생성한 음악, 영상 및 효과음이 서부극 분위기와 실제 전투 정보 전달에 기여하는가

따라서 AI의 코드 생성 완료를 기능 완료로 간주하지 않았다. 개발자가 플레이 화면과 수치를 확인하고 의도와 다르면 결과를 거절하거나 더 구체적인 조건으로 다시 지시하는 과정을 반복했다. 이것이 LOADED에서 AI를 활용한 핵심 방식이다.

### 8.4 구매 및 구독 증빙 관리

유료 Asset Store 에셋은 구매 내역을 보유하고 있으며 Kling AI, Suno와 ElevenLabs는 에셋 생성 당시 프리미엄 구독 상태였다. 심사나 권리 확인 과정에서 증빙이 필요한 경우 다음 자료를 별첨 이미지로 제출할 수 있다.

- Unity Asset Store 구매 내역 또는 영수증
- Kling AI, Suno와 ElevenLabs의 당시 프리미엄 구독 내역
- 생성 날짜, 계정, 트랙 또는 프로젝트를 확인할 수 있는 화면

증빙 이미지를 첨부할 때는 주문 번호 일부, 계정 이메일, 결제 수단과 주소 등 심사에 필요하지 않은 개인정보를 가리고, 에셋명, 구매 또는 구독 상태와 날짜만 식별 가능하게 남긴다.
