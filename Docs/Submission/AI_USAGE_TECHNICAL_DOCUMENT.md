# LOADED AI 활용 기술 문서

> 제출 전 확인: `OldMovieFx`의 실제 취득 경로와 Suno·ElevenLabs 결과물 생성 당시의 구독 플랜을 확인해야 한다. 확인을 마친 뒤 본 문서의 `확인 필요` 표시를 최종 정보로 교체하고 이 안내문은 삭제한다.

## 1. 프로젝트 개요

**LOADED**는 무작위로 획득하고 장전한 탄환의 조합과 발사 순서를 설계하여 적의 예고 공격을 돌파하는 턴제 탄창 빌딩 로그라이크 게임이다.

개발 과정에서는 OpenAI Codex와 ChatGPT를 기획 구체화, 기존 Unity 프로젝트 분석, C# 구현, 디버깅, 테스트 항목 작성 및 문서화에 활용했다. GPT Image, Kling AI, Suno와 ElevenLabs는 각각 이미지, 영상, 음악과 효과음 제작에 활용했다.

AI가 게임 전체를 자율적으로 설계하도록 맡기지는 않았다. 개발자가 먼저 전투 규칙, 플레이 감각, 정보의 우선순위와 시각적 기준을 결정하고, AI에는 이를 구현하기 위한 구체적인 조건을 전달했다. AI의 결과는 코드 검토, 컴파일, Unity Play Mode 확인, WebGL 빌드 및 실제 플레이 테스트를 거쳐 채택하거나 수정했다.

## 2. AI와 개발자의 역할

| 구분 | 개발자가 담당한 내용 | AI를 활용한 내용 |
| --- | --- | --- |
| 게임 설계 | 탄창 빌딩이라는 핵심 콘셉트, 턴 규칙, 탄환 효과와 시너지 설계 | 규칙의 예외 상황 정리, 구현 가능한 데이터 구조 제안 |
| 프로그래밍 | 기능 범위, 우선순위, 입력 방식, Inspector 연결 정책 결정 | 기존 코드 분석, Unity C# 구현, 리팩터링, 방어 코드 작성 |
| UX·연출 | 플레이 화면을 보고 문제를 판별하고 색상·속도·강조 순서 결정 | UI 생성 및 수정, 애니메이션과 셰이더 연결, WebGL 대응 |
| 밸런스 | 탄환 수치와 조합 의도 결정, 실제 플레이 결과 평가 | 피해 계산 검증, 극단 조합 탐색, 예상 피해 로직 구현 |
| 콘텐츠 | 채택할 이미지·영상·음악·효과음의 기준과 최종 선택 | 여러 시안 생성과 변형 |
| 검증 | Play Mode 및 WebGL 플레이, 시각·청각 품질 판단 | 정적 코드 검토, 컴파일, 테스트 조건과 회귀 항목 작성 |

핵심 원칙은 **설계와 최종 판단은 개발자가 하고, AI는 분석·구현·반복 수정의 속도를 높이는 도구로 사용한다**는 것이다.

## 3. 사용한 AI 도구

| AI 도구 | 활용 영역 | 주요 활용 내용 |
| --- | --- | --- |
| OpenAI Codex | 프로그래밍 | Unity C# 구현, 프로젝트 구조 분석, 리팩터링, 버그 수정, 컴파일 및 회귀 검증 |
| ChatGPT | 기획·개발 보조 | 기능 요구사항 구체화, 예외 상황 정리, 프롬프트 및 문서 초안 작성 |
| GPT Image | 그래픽 | 캐릭터, UI 아이콘과 오브젝트 그래픽 시안 제작 |
| Kling AI | 영상 | 정적 이미지를 기반으로 한 배경 및 캐릭터 영상 제작 |
| Suno | 음악 | 메인 메뉴, 전투, 보스, 상점과 게임 오버 BGM 제작 |
| ElevenLabs | 효과음 | 총격, 폭발, 적 공격 경고, 상태 효과와 UI 효과음 제작 |

생성된 모든 결과를 사용하는 방식이 아니라 게임의 서부극 분위기와 기능 전달에 맞는 결과만 선별했다. 사용하지 않기로 판단한 결과물은 최종 빌드에 포함하지 않았다.

## 4. AI 활용 개발 절차

```text
플레이 경험에서 문제 발견
        ↓
개발자가 의도와 우선순위 결정
        ↓
현재 프로젝트 구조와 제약 조건을 포함한 프롬프트 작성
        ↓
AI가 코드 또는 콘텐츠 생성·수정
        ↓
코드 검토와 컴파일
        ↓
Unity Play Mode·WebGL 실제 플레이 확인
        ↓
결과 채택 / 추가 수정 지시 / 폐기
```

프로그래밍 프롬프트에는 기능 이름만 적지 않고 다음 항목을 가능한 한 함께 전달했다.

- 기존 클래스와 데이터의 책임 범위
- 턴 소비 시점과 이벤트 호출 순서
- 정상 상황과 실패 상황의 기대 결과
- Inspector 참조를 유지할지 여부
- 런타임 자동 탐색 허용 여부
- 저장·불러오기와 WebGL 호환성
- 화면에서 확인할 수 있는 테스트 조건
- 수정하면 안 되는 기존 UI·프리팹·텍스트

이 방법은 AI가 기능 하나만 국소적으로 고치면서 기존 전투 흐름이나 직렬화 참조를 깨뜨리는 문제를 줄이는 데 도움이 되었다.

## 5. 프로젝트 구조와 AI 활용 지점

LOADED의 주요 구조는 데이터, 전투 실행, 표시 계층으로 나뉜다.

```text
ScriptableObject 데이터
BulletData / EnemyData / EnemyActionData / StageData / ItemData
                ↓
런타임 규칙과 상태
DeckManager / PlayerShoot / EnemyController / WaveManager / StateManager
                ↓
화면 표시와 피드백
PlayerCylinderUI / CombatFeedback / FirstRunGuide / WebGL Template
```

개발자는 각 계층의 책임과 데이터 흐름을 먼저 정의했다. Codex는 기존 파일과 참조 관계를 확인한 뒤 해당 구조를 유지하는 범위에서 코드를 구현했다. 예를 들어 탄환의 고정 수치는 `BulletData`, 강화도와 누적 스택은 `BulletInstance`, 덱·실린더·무덤 간 이동은 `DeckManager`, 실제 피해와 효과 처리 순서는 `PlayerShoot`이 담당하도록 분리했다.

## 6. 주요 AI 활용 사례

### 6.1 스테이지 타일 중앙 정렬

**사용 AI:** OpenAI Codex  
**개발자 판단:** 타일 수가 달라져도 화면의 중심이 흔들리지 않아야 하며, 홀수와 짝수 배열 모두 중앙 대칭이어야 한다.

대표 지시 사항은 다음과 같다.

> `BoardCount`만큼 타일을 생성하고 `BoardDistance` 간격으로 X축에 배치한다. 홀수 개라면 중앙 타일을 로컬 좌표 0에 두고, 짝수 개라면 중앙의 빈 공간을 기준으로 좌우 대칭이 되게 한다. 기존 Inspector 참조를 유지하고 null 참조와 중복 생성을 방지한다.

초기 결과는 시작점에서 한쪽 방향으로만 타일을 생성하여 전체 보드가 치우쳤다. 개발자는 이 결과를 채택하지 않고 중앙 대칭이라는 기대 결과를 다시 명시했다. 수정 결과는 다음 공식을 사용한다.

```text
startOffset = -(BoardCount - 1) × BoardDistance × 0.5
positionX = startOffset + BoardDistance × index
```

`BoardCount` 5와 4를 각각 대입해 예상 좌표를 확인하고 C# 컴파일을 통과한 뒤 적용했다. 이 사례를 통해 수학적 결과와 좌표 기준을 프롬프트에 함께 적어야 한다는 점을 확인했다.

### 6.2 탄환 덱과 실린더 전투 시스템

**사용 AI:** OpenAI Codex  
**개발자 판단:** 탄환은 단순 소비 자원이 아니라 순서와 조합을 설계하는 핵심 게임 시스템이어야 한다.

개발자가 정의한 기본 흐름은 다음과 같다.

```text
보유 덱 → 무작위 장전 → 6칸 실린더 → 순차 발사 → 무덤 → 재셔플
```

주요 지시 사항에는 ScriptableObject 기반 탄환 데이터, 덱·실린더·무덤 간 인스턴스 이동, 마지막에 장전한 탄환부터 발사하는 순서, 한 실린더 전체의 턴 소비 규칙, 연속 입력 방지와 UI 동기화가 포함되었다.

구현 후 실제 플레이에서 마지막 적을 이미 처치했는데 남은 탄환까지 허공으로 소비되는 문제가 발견되었다. 개발자는 다음 두 행동을 서로 다른 의도로 판단했다.

- 적을 향해 발사를 시작했다면 마지막 적 처치 후 남은 탄환을 보존한다.
- 처음부터 사거리 안에 적이 없었다면 의도적인 허공 발사로 보고 실린더 전체를 소비한다.

AI에는 이 판단과 함께 현재 체력, 보호막과 예약 피해를 이용해 매 발 유효 표적을 다시 확인하도록 지시했다. 구현 후 표적 발사, 허공 발사, 관통, 연쇄 사격, 상태 피해와 마지막 적 처치 상황을 구분해 회귀 검증했다.

이 사례에서 AI는 전투 규칙을 결정하지 않았다. 플레이어의 의도를 어떤 기준으로 구분할지는 개발자가 정했고, AI는 그 규칙이 모든 발사 경로에서 동일하게 적용되도록 구현했다.

### 6.3 예측 가능한 적 AI

**사용 AI:** OpenAI Codex  
**개발자 판단:** 로그라이크의 변수는 탄환 조합에서 만들고, 적의 공격은 플레이어가 관찰하고 대응할 수 있어야 한다.

따라서 전투 행동 선택에는 난수를 사용하지 않고 다음 상태를 각각 한 턴으로 분리했다.

```text
빈 행동 슬롯 → 행동 등록 → 공격 준비 → 공격 실행
```

공격 준비 단계에서 대상 타일이나 공격 방향을 고정하고, 실행 직전에 플레이어를 다시 추적하지 않도록 지시했다. 칼잡이, 총잡이, 투척병과 지원형 적에는 서로 다른 결정 규칙을 적용했지만, 모든 공격은 UI 행동 타일과 위험 타일을 통해 먼저 예고하도록 통일했다.

개발자는 실제 플레이에서 공격 예고와 실행 위치가 일치하는지, 플레이어가 이동하여 공격을 회피할 수 있는지, 기절이나 적 사망 시 남아 있는 공격 타일이 올바르게 정리되는지를 확인했다. AI는 상태 전이와 예외 처리를 구현하고 개발자는 정보가 공정하게 전달되는지를 최종 판단했다.

### 6.4 튜토리얼과 전투 UX 개선

**사용 AI:** OpenAI Codex  
**개발자 판단:** 튜토리얼의 원래 과제보다 플레이어의 생존과 현재 수행 가능성이 우선되어야 한다.

초기 가이드는 정해진 미션만 표시했기 때문에 적을 바라보지 않거나 사거리 밖에 있으면 피해 예상치를 확인할 수 없었다. 또한 장전이나 대기를 안내하는 도중 적에게 맞을 상황에서도 원래 미션을 계속 요구했다.

개발자는 다음 우선순위를 직접 정했다.

> 공격할 적을 바라보는 것보다 공격을 피하는 것이 우선이다. 피격 직전이라면 미션을 `적의 공격으로부터 회피하세요!`로 바꾸고 이동 버튼을 강조한다.

이를 바탕으로 AI는 현재 위험 타일, 플레이어 방향, 적의 위치와 탄환 사거리를 검사하여 임시 우선 미션을 만드는 구조를 구현했다.

```text
즉시 피격 위험 회피
    > 현재 미션을 수행할 수 있는 위치 확보
    > 적 방향 전환
    > 원래 튜토리얼 미션
```

시각적 품질 역시 개발자가 화면을 직접 보고 조정했다. 강조색이 배경과 섞인다고 판단해 색상과 투명도를 수정했고, 미션 변경 시 패널이 잠시 커졌다 돌아오는 연출을 추가했다. 가이드의 공격 준비 예시는 임시 효과가 아니라 실제 적 공격 준비에 쓰이는 머티리얼과 셰이더를 재사용하도록 수정했다. 사용 폰트에서 굵은 글씨의 획이 뭉개지는 문제를 발견한 뒤 모든 가이드 텍스트에서 볼드 표시를 제거했다.

이 과정은 AI가 제안한 첫 결과를 그대로 쓰지 않고, 개발자가 실제 화면에서 정보 전달력과 게임 분위기를 평가하며 반복적으로 수정한 사례다.

### 6.5 WebGL 저장과 로딩 화면

**사용 AI:** OpenAI Codex  
**개발자 판단:** 별도 설치 없이 실행되어야 하며, 브라우저 환경에서도 저장 안정성과 게임의 시각적 정체성을 유지해야 한다.

WebGL에서는 종료 콜백을 신뢰하기 어려우므로 전투 시작, 적 턴 종료, 상점 변경과 구매 완료처럼 상태가 안정된 시점에 자동 체크포인트를 저장하도록 구현했다. 저장 데이터는 WebGL PlayerPrefs와 브라우저 저장소에 기록하고, 기존 파일 기반 저장이 있으면 마이그레이션하도록 구성했다.

로딩 화면은 별도 영상 대신 HTML과 CSS로 6칸 실린더를 표현했다. 초기 결과에서 실린더의 회전 방향과 탄환이 들어가는 약실의 위치가 실제 게임과 달랐다. 개발자는 이를 시각적으로 비교한 뒤 다음 조건을 명시했다.

> 실린더는 시계 방향으로 정확히 60도씩 회전해야 하며, 회전 후 정렬된 약실에 탄환이 나타나야 한다. 길쭉한 탄환이 꽂히는 별도 연출은 사용하지 않는다.

AI가 CSS 회전과 약실 인덱스 계산을 수정한 뒤 실제 WebGL 로딩 순서와 게임 내 실린더 방향을 다시 비교했다.

### 6.6 이미지·영상·음악·효과음 제작

그래픽과 영상은 AI가 만든 첫 결과를 그대로 사용하는 대신 다음 기준으로 선별했다.

- 서부극과 픽셀 아트의 색감이 기존 UI와 일치하는가
- 작은 아이콘에서도 기능을 알아볼 수 있는가
- 반복 영상의 시작과 끝이 자연스럽게 연결되는가
- 캐릭터 실루엣과 이동 방향이 게임 플레이를 방해하지 않는가

Kling AI로 제작한 기차역 배경 영상에는 영상 길이, 기차의 이동 방향, 등장 시점, 통과 시간과 먼지가 사라지는 시간을 구체적으로 지정했다. 반복 구간이 어색하거나 게임 화면과 원근이 맞지 않는 결과는 제외하고 필요한 부분만 편집했다.

Suno에는 일반 전투, 보스전, 상점과 메인 메뉴의 역할을 나누어 서부극·플라멩코 계열 악기, 템포와 공격성을 지시했다. ElevenLabs 효과음은 총격, 폭발, 경고음, 상태 효과와 UI 피드백 용도로 생성했다. 기계적이거나 미래적으로 들리는 결과, 다른 효과음에 묻혀 정보 전달이 약한 결과는 채택하지 않았다.

## 7. 검증 방법과 개발자 판단

AI 결과는 작업 성격에 따라 다음 단계로 검증했다.

1. 수정 파일과 영향 범위를 확인한다.
2. 상태 변경 순서, null 처리, 턴 소비와 저장 시점을 코드로 검토한다.
3. `dotnet build`로 C# 컴파일 오류와 경고를 확인한다.
4. Unity Play Mode에서 정상 입력과 예외 상황을 재현한다.
5. UI, 애니메이션, 사운드와 셰이더는 실제 화면과 게임 분위기를 기준으로 확인한다.
6. WebGL 전용 기능은 브라우저 빌드에서 로딩, 오디오 활성화, 저장·불러오기와 화면 배치를 확인한다.
7. 요구사항을 충족하지 못하면 추가 지시하거나 직접 값을 조정하고 다시 검증한다.

정적 코드 검토나 컴파일만 수행한 항목은 실제 플레이 검증이 끝난 것처럼 기록하지 않았다. 개발 기록에는 검증한 범위와 수동 확인이 남은 범위를 구분하여 작성했다.
